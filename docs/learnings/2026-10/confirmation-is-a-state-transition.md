# 确认不是第二次保存

## 为什么值得区分

“保存字段 → 再确认已保存字段”看似稳妥，却容易让界面显示正在编辑的值，而服务端确认旧值。用户理解的确认对象是眼前的摘要，不是数据库里某个看不见的历史版本。

更清晰的设计是：一次显式确认携带完整摘要和读取时的版本。服务端在一个短事务里检查版本、合并摘要、标记确认；失败整体回滚，成功版本只加一次。普通草稿编辑仍可保留独立保存入口，但不能要求所有用户经过两次操作。

## 两个不能混淆的状态

- **信息来源**：用户自述的基础，不等于练习验证的能力。缺失字段的默认值也不是用户的承诺。
- **授权状态**：模型生成了路线，不等于用户同意路线。反馈得到的新草稿仍然需要显式发布。

因此，“跳过”应保存为独立事实，而不是伪造一个填好的答案；默认假设应该在确认前可见，并进入生成上下文。学习状态只能由原有练习规则推进。

## 异步刷新下的陷阱

刷新可以更新服务端版本，但不能覆盖本地未确认摘要或未保存图谱。分别跟踪目标与图谱的 dirty 状态，用请求序号淘汰迟到读取；有任一未确认编辑时阻止发布。不要为了让按钮可点而静默丢掉用户编辑。

响应丢失不是业务拒绝：先只读查询，再由用户显式恢复原 request_id 的模型任务。不能刷新就创建一个新任务，也不能把网络错误当作“肯定没有提交”。

自检：用户看见的摘要与服务器确认的内容是否一致？默认假设能否和自述区分？反馈成功后是不是仍然草稿？
