# Skill 是方法，不是权限

## 为什么不要把所有流程都塞进 system

模型每次需要知道“有哪些方法”，但不一定需要知道每一种方法的完整步骤。把十份指南全部展开会挤掉业务上下文和历史，还可能让互不相关的流程干扰当前任务。

渐进披露把两件事拆开：名称与描述帮助选择，正文指导执行。Skill 文件可以在启动时全部读取和校验，但模型上下文仍按需加载；“懒加载”不必意味着每轮访问磁盘。

## 方法与能力必须分开

Skill 可以建议“理解检查后再出题”，但不能凭这句话创建一个原本不存在的出题权限。宿主确定工具白名单和作用域，领域代码确定判分与发布规则，Skill 只指导已有能力的组合。

因此，按模式过滤 Skill 是减少干扰，而不是完整授权系统。即使某份指南提到发布图谱，模型也不能执行没有注册的发布工具；人工确认不能被一段更详细的 prompt 替代。

## 最容易忽略的是输入来源

字段叫 user_text 不一定意味着它来自用户。学习包解释会把组件正文和事件拼成模型输入；扫描其中的 $skill-name 会把业务数据误认为显式用户选择。

判断能否激活技能时，要问“是谁构造了这段文本”，而不是“消息的 role 或字段名是什么”。当前聊天输入可显式选择技能；资料、历史、结构化答案和事件合成输入不能。中文标记的边界也应按 ASCII 技能 ID 定义，而不是使用包含汉字的 Unicode 单词边界。

## 历史不是当前配置

技能正文作为工具结果保存后，下一轮会随协议历史回来。技能已经更新或本轮不再适用时，旧正文不应重新成为流程指令。

也不能直接删除那条 tool 消息：assistant 的 tool_calls 还引用它，删除会破坏协议。应保留配对，只投影旧结果为历史提示，同时保留原持久记录供追溯。call ID 可能跨回合复用，必须在每组 assistant 调用范围内识别技能工具，不能用全局 ID 集合替换所有同名结果。

## 自检

- 新增一份指南，是否意外新增了文件访问或写工具权限？
- 显式触发文本到底来自用户，还是业务产物？
- 旧工具结果是否被当作当前有效配置，历史处理是否保留协议配对？
- 外层 Agent 读过指南，内层独立模型调用真的获得它了吗？
