# 一次执行的预算与一次业务操作的身份

一次教学任务可能先让模型决定出题，再由生成器调用模型、修复 JSON，最后由主循环回复。若每个模块独立计数，“最多六次”就会变成每个模块各六次。应在最靠近模型端口的位置包装一次 gateway，所有调用共用父 run 的计数和 usage。Runner 不再额外计数；遇到同预算包装器直接复用，避免一次请求算两次。

执行次数与业务产物身份解决的是两件事。出题成功后，最后回复可能失败。用户重试需要新的 run 和新的执行预算，却应拿回已经保存的题目。若使用 run ID 或 tool_call ID 去重，重试会新增题目。稳定 operation key 应使用保留到重试的 root task，以及操作类型、节点、内容版本和固定槽位。count/purpose 作为参数 fingerprint：同键同参数复用，同键不同参数报冲突。只有用户另起新任务才分配新 root。

去重还需要原子提交。先在事务外生成并校验整批候选，再在短事务内读取最新状态、检查 operation、版本和重复题，保存题目与 operation。SQLite 的 `BEGIN IMMEDIATE` 串行化竞争写入，主键约束保证操作身份唯一；两个生成器即使都已调用模型，也只能保存一批。幂等不代表供应商绝不重复调用，它保证业务副作用不重复。

两个常见陷阱：私有候选/修复消息回注教学 transcript 会提前泄露答案；分别读取 planning 和 learning 后只锁 learning，仍不能证明规划版本与写入完全原子。前者靠公共题目投影，后者需要后续统一事务或同步协议，不能靠一次重读宣称消除竞态。

当前实现与验证见[对应 history](../../histories/2026-10/20261013-1840-exercise-generation-budget.md)。run/root 关联仍在内存，因此已持久化的 operation 不等于能够通过旧 run ID 跨进程重试。
