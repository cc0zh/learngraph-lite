# Agent 主动编排，不等于 Agent 拥有决定权

## 是什么

规划 Agent 可以从自然语言提取事实、决定要问什么、创建草稿和解释修改；但“用户同意了”和“方案正式生效”是不同的业务事实，不能由模型推断或自写。

原先的固定问卷和一次 JSON 生成容易验证，却缺少连续协作：用户回答只改变表单，模型看不到这一轮问答如何发生。反过来，把所有能力都交给模型工具，又会让“请用户确认”的提示词变成唯一门禁。

## 怎么想

把能力分成三类：

| 能力 | 谁控制 | 为什么 |
| --- | --- | --- |
| 理解、发问、解释与草稿建议 | Agent | 输入和问题因人而异，不适合固定流程 |
| 等待用户、预算、协议配对、版本与取消 | 宿主程序 | 提示词不能保障运行边界 |
| 确认目标、发布路线 | 用户操作 + 确定性接口 | 不能把模型说“你同意了”当作授权证据 |

发出问题卡或目标审核卡后，本轮应结束，而不是占着线程等人回来。下一轮从持久化问题、结构化答案和合法协议历史恢复上下文。

## 一个容易踩的坑

模型一次返回多个工具调用：第一个发出了问题卡，第二个准备写草稿。仅在工具结果里返回 `waiting_for_answer=true` 不够；模型或 Runner 仍可能执行第二个工具。

正确的宿主语义是：成功的结束轮次工具触发停止；剩余调用不执行，但仍补齐对应工具结果，保持 assistant tool_calls 与 tool_call_id 的协议配对。错误参数则允许模型修复，不把失败当作成功的等待状态。

另一个坑是只把答案拼成“选了 A”。应保留原问题 ID、跳过状态和来源轮次，后端检查作用域与版本；否则刷新或旧卡重复提交会在新目标上错误生效。

## 可复用的原则

1. 对话是协作记录，领域快照是当前事实；不能只从聊天措辞判断发布状态。
2. 审核卡保存生成时版本，操作前核对当前版本；历史卡可读，不代表仍可操作。
3. 确认后继续生成是用户操作授权的新请求；刷新和响应丢失恢复只能读取，不自动继续调用模型。
4. 差异由程序计算，理由由模型解释，避免模型声称删掉了实际仍存在的内容。
5. fixture 只能证明协议和交互闭环，不能证明真实模型总能理解用户或生成好路线。

## 自检

- Agent 一次发问并请求发布，代码会执行什么？
- 用户刷新页面后，哪些状态能恢复，哪些动作必须再次显式触发？
- 用户说“好”与点击当前版本的确认按钮，为什么不能等价？
