# 并发 Agent 的作用域应绑定到一次请求

一个模型客户端可以服务多个学习目标，但“当前目标”不能是共享的可变属性。假设请求 A 设置 `current_goal = A` 后等待模型，B 又把它改成 B，A 随后的工具调用就可能读取 B 的成绩。单线程手动演示通常发现不了这个问题。

更直接的做法是每轮创建工具注册表，用闭包捕获服务器确认的 `goal_id` 和 `node_id`，再把注册表交给本轮 Runner。模型只需要选择工具和提供 `available_minutes`；它不需要重新指定目标。这样作用域来自请求，工具结果来自 repository，推荐规则来自领域服务，各自有明确来源。

上下文装配也在进入 Runner 前完成：system 消息保存应用指令，单独的 JSON 消息保存目标、节点和表现，最后保留用户本轮原文。把 JSON 标为业务数据有助于模型理解消息用途，但提示词本身不能代替工具参数校验；本实现使用严格 Pydantic 参数模型与服务端绑定，仍需真实模型评测判断回答质量。

绑定 ID 还不够，数据也有版本。同一节点 ID 在新图谱中可能已有不同内容。读取时比较已发布规划图谱与学习快照，避免把旧成绩用于新节点；同一 run 中发现版本变化应返回可修正的工具错误。只读操作不该偷偷调用 `start_goal()`，因为那会重置成绩。后续应通过显式迁移用例决定哪些成绩可保留。

验证要制造会出现问题的交错：让两个目标的首次模型调用在 barrier 汇合，再各自调用工具，确认返回自己的 goal。另用重新打开的 SQLite repository 验证持久数据，用修改并重新发布图谱的场景验证过期拒绝。单纯检查闭包变量或 mock 方法被调用一次，不能覆盖这些行为。

当前实现没有跨 planning/learning repository 的事务，也不提供会话历史或图谱迁移协议；这些限制不能由上述测试推导为已解决。实现与证据见 [execution plan](../../exec-plans/active/learngraph-lite-implementation.md#节点学习上下文与只读业务工具切片已完成)。
