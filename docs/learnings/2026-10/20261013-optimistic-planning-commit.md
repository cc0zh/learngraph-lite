# 慢生成与乐观提交

模型生成可能耗时数十秒，用户仍能在此期间编辑目标。若把生成放进数据库事务，会长时间占写锁；若只在生成前检查版本，晚到草稿又可能覆盖用户编辑。解决办法是先读取快照并在事务外生成，再在短写事务中检查版本和保存结果。

```text
读取 version=3 → 模型生成 → BEGIN IMMEDIATE
                              检查仍为 3 → 保存草稿并写 version=4 → COMMIT
                              若已为 4 → 拒绝旧候选并回滚
```

两个版本回答不同问题：planning version 表示目标、问题或草稿是否被写过；graph revision 表示发布路线的领域修订。编辑草稿会改变前者，却还没有产生新的发布修订。发布时检查二者，才能同时避免过期审核与过期路线操作。

另一个易漏的竞争发生在提交后：保存草稿，再 GET 当前状态作为任务输出，可能读到另一位操作的编辑。输出应由本次保存结果构造，保留准确版本；最新状态由独立 GET 获得。两者都合理，但含义不同。

同样要分清取消终态与提交事实。取消标志应在事务内再次检查，但提交之后才到达的取消不能撤销已落库事实。没有持久 operation registry 时，应先读取最新状态再决定重新生成，不能把旧 expected_version 直接当成可重试凭据。

该版本锁只保护同一 planning 聚合。它不自动覆盖资料绑定、学习初始化等其他仓库；两个仓库各自成功不等于跨仓库原子成功。若跨仓库一致性成为验收项，就需要共享事务或明确可恢复的初始化协议。

实现与限制见 [执行计划](../../exec-plans/active/learngraph-lite-implementation.md#目标澄清与图谱生成-http-切片已完成)。自检：用户在生成时编辑会发生什么？为什么不能把提交后的 GET 当成本次输出？
