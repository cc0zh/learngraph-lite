# 为什么取消任务后不能立即释放并发名额

点击“停止”后，界面应尽快进入取消状态。但 Python 线程里已经发出的同步模型请求，可能还在等待网络响应。这里有两个不同的时间点：**用户可见任务结束**，以及**执行代码实际退出**。

如果取消时立即归还并发名额，就能不断提交、取消、再提交；每次界面都说任务已停止，后台却累积更多阻塞请求。最多两个活动 run 的限制也就失去了作用。

## 把状态结束与资源释放分开

应用层在同一把锁下处理取消：设置预算的取消标志、提交唯一终态、通知 SSE 订阅者。线程仍占用执行名额；它收到模型结果后检查取消标志，不继续工具或下一轮模型调用，最后在 `finally` 中释放名额。

```python
# 用户取消：公开状态立即结束，执行名额仍保留。
budget.cancelled = True
finish_once(record, "cancelled")

# 工作线程：无论成功、异常还是取消，都在实际退出时归还名额。
try:
    result = runner.run(messages, budget)
    if record.status not in TERMINAL_STATUSES:
        save_result_and_finish(record, result)
finally:
    release_capacity(record.run_id)
```

上面省略了锁。真实实现中的取消、结果检查和终态提交必须互斥，否则晚到的结果仍可能覆盖取消状态。

## 这为什么叫协作取消

同步线程不能安全地强行中断另一个线程。预算标志只会在代码下一次检查时生效，因此模型/工具适配器本身必须配置有限超时。应用关闭也遵循相同规则：先停止准入并取消任务，再等待执行退出。若适配器永远不返回，关闭也会一直等待。

还要检查服务框架的关闭顺序。Uvicorn 先等待连接与 HTTP 任务结束，再调用应用的 lifespan shutdown。如果 SSE 一直等待活跃模型，放在 lifespan 里的取消就到不了。启动入口设置有限的 graceful shutdown 时间，让连接等待结束后能进入应用清理；它限制的是连接等待，无法代替模型调用超时。

连接断开则是另一件事：浏览器可能只是刷新或切换网络。SSE 的关闭只结束订阅，不应自动取消任务；重连后读取当前快照即可。

## 怎样验证，才不会被“看起来取消了”骗过

使用带 `Event` 的阻塞假模型，不依赖固定 sleep：

1. 启动两个 run，等待模型确认进入阻塞调用。
2. 取消其中一个，断言查询和 SSE 立即显示唯一取消终态。
3. 在释放模型之前提交第三个 run，仍应被全局并发限制拒绝；同 session 也仍忙碌。
4. 放行模型，断言晚到文本或工具调用没有覆盖终态，也没有继续执行工具。
5. 等待工作线程退出后，才应能再次提交任务。

这些检查分别证明公开状态、资源边界和后续行为。仅断言 `status == "cancelled"` 无法证明后台执行已经受控。

自检：你的取消按钮释放的是界面状态，还是实际执行资源？一个慢响应到达时，谁负责保证终态不会被二次提交？
