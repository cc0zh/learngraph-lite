# 接受提案为什么必须是一个事务

一份学习路线不只存在于图谱表：规划快照决定学什么，学习快照决定题目和统计对应哪个版本，提案状态证明用户是否接受。三个对象一起变化，才是有效的审核。

## 三次 save 的陷阱

| 写到哪一步崩溃 | 留下的状态 |
| --- | --- |
| 新图谱已保存，学习版本未更新 | 新节点搭配旧题和成绩，或上下文持续拒绝不一致 |
| 学习已迁移，提案仍 pending | 再点接受可能重复推进版本 |
| 提案先 accepted，图谱保存失败 | UI声称成功，业务事实却未改变 |

“每张表用了事务”不够，它们必须属于**同一个提交边界**。

## 短事务围住决定，不围住模型

模型在事务外生成候选；接受时没有网络调用。应用依赖协调端口，SQLite适配器在一个连接执行：

```text
BEGIN IMMEDIATE
  读取规划、学习、提案和去重记录
  校验 goal / expected revision / base revision / 状态
  构造下一图谱和学习快照
  保存规划 + 学习 + 提案状态
COMMIT
```

任一保存失败全部回滚；两个并发接受串行检查，只有首次推进。conflicted是需要保存的业务结果，应先提交它，再向HTTP返回409，而非抛异常回滚冲突事实。

## 版本不是删除历史

语义或依赖改变时推进content_revision，旧题/attempt/package仍保留，当前统计只看新版本证据。priority/minutes只推进计划revision，可以沿用内容证据。本项目采用全局内容版本，简单可验证，但保守失效未直接改变的节点，不能称作节点级最小迁移。

只读工具不能为了“正常显示”重置成绩。教学生成也必须绑定原回合图谱：每次上下文检查及最终保存拒绝悄悄切换版本。模型在事务外运行的长时间，不是跨版本写入许可。

## 怎么验证

- 注入第二/第三次保存失败，三份状态保持原值。
- 并发和同向重复接受只推进一次；反向决定冲突。
- 重开SQLite后图谱/学习版本与提案状态一致。
- 接受响应丢失，浏览器只GET同步图谱/状态，不猜测服务端未执行。
- 旧题/包可读但不产生新成绩；历史反馈不污染新版本统计。
