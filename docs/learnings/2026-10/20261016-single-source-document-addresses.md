# 同一份 Markdown，为什么会有两种链接地址

为仓库文档接上静态站，不只是“让 Markdown 变成 HTML”。真正容易出错的是：**文件地址与站点地址不是同一个坐标系。**

## 先分清两个坐标系

假设文件在 `docs/developer/concepts.md`，链接写成：

```markdown
[贡献指南](../../CONTRIBUTING.md)
```

在仓库中，这个相对路径指向根目录的贡献文档，是正确的。若网站移除了 `docs/` 前缀，该页地址变为 `/developer/concepts.html`。浏览器只按 URL 解析，不知道原来的源码目录；照搬路径可能逃出站点子目录，或落到一个并未构建的页面。

可靠的转换顺序是：

```text
原文相对链接 + 原文件位置
          ↓ 先解析
仓库中的真实目标文件
          ↓ 再做路由映射
站点中的目标页面 + 原 query/hash
```

不要先重写当前页的位置，再拿新位置猜原链接；本地搜索还可能使用与页面编译不同的渲染环境，转换器要兼容两条入口。

## 同源不等于复制一份

为网站复制根级 README 或 CONTRIBUTING，初次实现最省事，却会产生第二份事实。更合适的是直接选择正式 Markdown 作为构建输入，再将它们映射到稳定路由。对 LICENSE 这样的非 Markdown 原文，可以用包含机制呈现，而不手工同步法律文本。

同时检查映射是否一对一：根 `SECURITY.md` 是漏洞反馈，`docs/SECURITY.md` 是实现约束。去掉 docs 前缀后都叫 `/SECURITY.html`，即使没有缺失文件，也可能悄悄覆盖或读到错误页面。应为其中一个分配独立路由，并用浏览器读取两页验证内容不同。

## 两种门禁证明不同的事情

| 检查 | 能证明 | 不能证明 |
| --- | --- | --- |
| 仓库链接检查 | 相对目标文件存在、未越出仓库 | 对应页面已构建、路由未冲突 |
| 静态站构建 | Markdown 可编译、站内页面路由可达 | 所有锚点正确、内容符合源码 |
| 浏览器回归 | 用户能导航、搜索、在手机阅读 | 历史描述仍代表当前实现 |

例如工具脚本存在，不代表它应该被网站当 HTML 页面发布。源码路径保留为编辑器路径，比生成一个假的源码页面链接诚实。

## 搜索还有时间维度

版本化历史很重要，但旧计划可能仍写着已删除页面。保留历史的浏览链接，同时从默认搜索中排除旧计划和验收记录，可以减少“搜索命中但事实过时”的误导；当前指南继续指向唯一质量状态来源，而不是复制验收数字。

生成缓存也不是正式知识：不能因为它位于 `docs/` 就纳入链接门禁或源码归档。应分别测试“主题源码被保留”和“缓存/临时包/构建物被排除”。

## 自检

2. 两个不同文件会不会变成同一个站点路由？
3. 新人搜到的第一条结论，来自当前指南还是旧验收材料？
