# 为什么逻辑任务与执行 attempt 要分开

一次解释可能经历模型失败、用户取消和进程退出。如果每次重试都当成新任务，已经生成的题或学习包就容易重复保存；如果始终覆盖同一个 run，失败经过又会丢失。因此需要两种身份：逻辑任务表示“我要完成什么”，attempt 表示“这一次怎么执行”。

本项目用 `(goal,event,slot)` 标识解释任务，root_task_id 贯穿它的所有 attempt；run_id 每次显式重试都新建。request_id 解决一次请求的重复提交，业务键解决多个不同请求表达同一件事。两者不能互相代替。原始 request_id 仍读取原 attempt，新的业务重复请求读取最近 attempt；若产品要求每个重复请求都永久绑定当时结果，就要保存别名，而不能只靠内存推断。

## 先建立身份，再执行模型

假设先建立事件到 root 的关联，再另存初始输入和 run：两次写入之间退出，会留下“关联存在、任务不可查询”的状态。倒过来也不可靠，会留下无法判断属于哪个逻辑任务的 run。应把关联、初始请求和 queued run 放进同一个短事务，成功后才允许模型执行。

模型调用可能耗时或失败，不应占用数据库写事务。执行期间其他 ACK 和查询仍应可用；完成时再用短事务同时提交结果与终态事件，避免 GET 显示 completed、SSE 却没有完成事件。内存状态也应在持久化成功后更新。

## 重启是一条明确的状态转移

重启看见 running，不知道供应商是否已收到请求、是否已经产生费用，也不知道业务产物是否已保存。把它标成 interrupted，让用户显式 retry，比自动再次请求更容易理解和验证。重试沿用原 root 与初始输入，业务生成用稳定 operation key 查找已保存产物，必要时可以零模型调用完成新的 attempt。

这里仍然不能承诺模型调用恰好一次：进程可能在供应商成功后、本地提交前退出。能够保证的是本地准入原子性、可查的 attempt 历史，以及已提交产物按逻辑任务复用。这些保证分别需要事务、状态机和幂等 operation，单有 request_id 不够。

自检：run 状态保存失败时，你会报告未持久化的成功吗？取消后底层调用还没退出，能立即释放并发名额吗？如果回答是“会”或“能”，就可能让公开状态超出实际执行与恢复能力。
