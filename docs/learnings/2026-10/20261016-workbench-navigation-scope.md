# 单入口不等于单一状态范围

把多页应用合进工作台时，最容易误做的是“所有目标参数都叫 goal，所有导航都替换掉 URL”。界面看起来统一了，状态的归属却混在一起。

## 先问：这次操作改变谁的事实？

一条学习会话有固定的目标和节点；浏览图谱、阅读另一目标的资料，只改变当前查看位置，不应偷偷改写会话。将 URL 分成独立范围：

```text
?goal=G&session=S                         原会话
&tool=document&document=D&chunk=C         资料工具与阅读位置
&source_goal=H&source_node=N              来源/绑定范围
```

`source_goal` 缺席可以回落当前会话；`source_goal=` 则表示用户明确清空。不要用 `value || fallback` 把两者压成同一个状态；先用 `has()` 区分缺席，再使用 `??` 选择默认值。

## 同一条导航也有生命周期

删除资料已经在服务器完成，并不意味着迟到的响应还拥有导航权。请求发起时记住起点；组件已卸载或用户已离开时，不再自动跳转。忽略旧响应的 UI 效果，不等于撤销服务器写入。

浏览器 Back 更特殊：`popstate` 到达时历史指针**已经移动**。取消离开后用 `replaceState` 会覆盖刚退到的上一项，而不是回到原项。为应用内历史项保存索引，取消时用反向 `history.go(delta)` 回原项并抑制这次恢复事件；测试必须再做一次 Back/Forward，单次“URL 看起来没变”不足以证明历史正确。

## 自检

- 阅读另一目标的原文后返回，会话 ID 和节点是否完全没变？
- 显式清空来源与未选择来源，刷新后是否仍能区分？
- 取消 Back 后再次 Back、Forward，是否仍访问原来的历史项？
- 用户已开始新操作时，旧请求还能把界面带走吗？
