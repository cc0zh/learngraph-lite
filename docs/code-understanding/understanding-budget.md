# 理解预算：按风险分层，不追求均匀理解

"所有代码都值得深度理解"这个隐含假设不成立。理解力是稀缺资源，而 Agent 的产出速度远超人的吸收速度——均匀分配注意力的结果是处处浅尝辄止，最需要深读的地方反而没读透。正确的做法是像管理资金一样管理理解力：**给不同风险等级的代码分配不同深度的理解**。

## 三个理解层级

| 层级 | 适用代码 | 理解深度 | 具体动作 |
|---|---|---|---|
| **L1 深读** | 核心领域逻辑、安全 / 权限、并发 / 状态机、公共 API 契约、数据迁移 | 能复述设计、能亲手改 | 逐行读；过 [`explain-diff.md`](explain-diff.md) 的测验；必要时亲手改一小块来验证理解 |
| **L2 边界** | 胶水代码、集成适配层、UI 装配、配置接线 | 理解接口与契约，不深究内部 | 只读函数签名、输入输出类型、错误路径；确认边界行为有测试覆盖 |
| **L3 结果** | 一次性脚本、代码生成产物、实验性 spike | 只验证产出结果正确 | 看运行结果 / 产物本身，不读实现 |

## 分层判断信号

判断一段代码属于哪一层，问三个问题：

1. **改错的代价有多大？** 出 bug 会造成数据损坏、安全事故、难以回滚的状态（→ L1），还是只是显示异常、容易回滚（→ L2 / L3）？
2. **未来还会不会碰它？** 它是长期演进的核心、后续改动都要经过它（→ L1），还是写完基本不再动（→ L2 / L3）？
3. **我的下一个想法依赖它吗？** 后续功能设计需要以它为基础来推理（→ L1），还是它只是一个被调用的黑盒（→ L2）？

任何一个问题指向高风险，就往上升一层。拿不准时升不降。

## 反模式

- **均匀深读**：给 500 行胶水代码逐行 review，结果没精力看 50 行核心状态机。
- **全部放过**：以"Agent 会自己验证"为由，对核心逻辑也只看结果。L1 代码不理解，就是认知债务的本金。
- **层级固化**：一次性脚本被提拔为常驻定时任务，却还按 L3 对待。代码的层级会漂移，被复用、被依赖时要重新评估。
