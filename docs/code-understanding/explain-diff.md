# explain-diff：为一次代码改动生成讲解文档

在 Agent 完成一次较大改动后（或你 review 他人的 PR 前），让 Agent 按本规范生成一份"讲解文档"（explainer）：先补背景、再讲直觉、然后走读代码、最后用测验检验理解。**读原始 diff 之前先读它。**

来源：Geoffrey Litt 的 [/explain-diff skill](https://gist.github.com/geoffreylitt/a29df1b5f9865506e8952488eac3d524)。本版本做了中文化和三处增强（见文末"与原版的差异"）。

## 使用规则

- 测验不通过，不把代码发给别人；review 别人的代码时同样先过测验。
- 测验是速度调节器：与 AI 协作时循环很容易跑得比人的理解快，测验强制你回答"我真的懂了吗"，让你保持创作参与者的身份。
- 什么改动值得生成讲解文档，按 [`understanding-budget.md`](understanding-budget.md) 判断——L1 层级的改动默认生成，L2 / L3 一般不需要。

## 给 Agent 的提示词（粘贴用）

```text
请为〔指定的代码改动 / diff / branch / PR〕生成一份丰富的交互式中文讲解文档。

必须包含以下四节：

1. 背景（Background）：讲解与这次改动相关的既有系统（需要广泛探索周边代码）。
   读者的水平未知，所以先给一段面向新手的深背景（并注明熟悉者可跳过），
   再给一段与本次改动直接相关的窄背景。

2. 直觉（Intuition）：讲清这次改动的核心直觉。重点是本质，不是全部细节。
   用带玩具数据的具体例子，大量使用图示。

3. 代码走读（Code）：高层次走读这次改动。优先按"一条执行路径"组织讲解顺序
   （从入口到终点按时间序讲，每步标注文件位置），而不是按文件字母序罗列；
   改动不构成单一路径时，再按可理解的逻辑分组。

4. 测验（Quiz）：
   - 五道中等难度的交互式选择题：必须真正理解这次改动的实质才能答对，
     但不出偏门陷阱题。读者点击后告知对错并给出反馈解释。
   - 最后加一道开放复述题："用你自己的话概述这次改动：目标、方案、
     最重要的取舍。"并提供一个默认折叠的"对照要点"块（列出 3–5 个要点），
     供读者自查复述是否完整。

格式要求：

- 输出一个自包含的单文件 HTML（内联 CSS 和 JavaScript）。整体是一页长文，
  带章节标题和目录，顶层结构不要用 Tab。做基本的响应式，手机上也能读。
- 文件放在代码仓库之外的固定位置，文件名以当天日期开头（保持按时间排序、
  不进版本控制），使用系统临时目录：Windows PowerShell 为 `$env:TEMP`，macOS/Linux 为 `/tmp`；
  例如 `2026-07-05-explanation-<改动主题 slug>.html`。
- 文风清晰流畅、经典风格，节与节之间过渡自然。
- 图示建议：选少数几种可复用的"图示家族"贯穿全文解释不同案例，比如：
  - 应用 UI 的极简示意版，用于解释界面改动；
  - 组件间数据流 / 通信的系统图，图里必须带示例数据。
- 不要用 ASCII 图。图一律用简单的 HTML 结构实现，列表用 HTML 列表。
- 代码块一律用 <pre> 标签。如果用自定义 div 代替，其 CSS 必须包含
  white-space: pre-wrap，否则浏览器会把换行折叠成一行。
  保存文件前，逐个检查 HTML 源码中每个代码块的 CSS 包含
  white-space: pre 或 pre-wrap。
- 用 callout 样式呈现关键概念定义、重要边界情况等。
```

## 与原版的差异

1. **输出中文**（原版为英文，文风参照 Martin Kleppmann）。
2. **测验增加一道开放复述题**：选择题存在蒙对的可能，复述没有——主动回忆是更强的理解检验。
3. **代码走读优先按执行路径组织**：与 [`trace-path.md`](trace-path.md) 呼应，叙事线比文件清单更容易吸收。
