# 路径叙事：让 Agent 沿一条具体路径讲代码

按文件读代码，得到的是零件清单；沿一条执行路径读代码，得到的是故事。人记得住的是故事。

这是成本最低的理解手段：一句提问，不产出任何工件，适合随时使用——接手陌生模块、review 前热身、或者只是想确认自己对某条链路的心智模型没有过期。

## 核心模板

> 给我讲一遍：〔某个具体动作〕之后，数据从〔入口〕到〔终点〕的完整路径。

例："给我讲一遍：用户点击『发送』按钮之后，这条消息从前端入口到落库的完整路径。"

关键是**具体**：要有真实的按钮名、真实的接口名、真实的表名。"讲讲消息模块"得到的是模块简介，"讲讲这条消息怎么落库"得到的才是叙事线。

## 变体

| 变体 | 提问方式 | 适合场景 |
|---|---|---|
| 一次请求 | 「这个 API 被调用后，从路由到响应返回经过了什么」 | 理解后端分层 |
| 一次定时任务 | 「这个 cron 触发后，从调度到落盘的完整过程」 | 理解异步 / 后台链路 |
| 一个错误的传播 | 「如果第 X 步抛错，错误怎么一路传播、用户最终看到什么」 | 理解错误处理设计 |
| 一次启动 | 「进程从启动到就绪，按顺序初始化了哪些东西、为什么是这个顺序」 | 接手新项目 |
| 一个数据的生命周期 | 「这条记录从创建、变更到删除 / 归档，都被谁碰过」 | 理解数据模型 |

## 对 Agent 输出的格式要求（粘贴用）

```text
请沿这条路径按时间顺序叙事，要求：

1. 一步一段，按实际执行顺序讲，不要按文件分组。
2. 每一步标注代码位置：文件路径 + 函数名，让我可以直接跳过去看。
3. 用一份具体的示例数据贯穿全程：展示它在每一步长什么样、发生了什么转换。
4. 明确标出协议转换点：HTTP → 内部对象、DTO → 领域实体、序列化 / 反序列化的位置。
5. 明确标出分叉点：哪一步可能失败、哪一步有条件分支，正常路径之外还有什么去向。
```

## 何时沉淀为可交互产物

如果一条路径值得反复查看、或需要讲给整个团队听，就不要停留在一次性的文字回答——按 [`ARCHITECTURE_GRAPH_GUIDE.md`](ARCHITECTURE_GRAPH_GUIDE.md) 把它做成讲解式单文件 HTML。那份指南的"案例叙事"原则（选一条端到端链路、每步展示此刻的数据）正是路径叙事的可视化版本。
